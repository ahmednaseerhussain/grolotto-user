GROLOTTO PLATFORM – COMPLETE DETAILED CHANGE REQUEST AND FIX DOCUMENT

Purpose of this document
This document explains in detail all requested changes, corrections, improvements, and missing
logic for the GroLotto platform, including:
• Vendor App
• Player App
• Admin App / Admin Panel
• Shared platform-wide behavior

This document must be used by the development team as a feature correction and
implementation guide. The goal is to make sure the platform behaves exactly as requested, with
proper currency separation, approval flow, payout flow, notifications, multilingual support, and
better performance.


================================================================================
1. VENDOR APP – DETAILED REQUIREMENTS
================================================================================

1.1 Vendor type and currency separation

Requirement
There are 2 types of vendors on the platform:
• HTG Vendor
• USD Vendor

A vendor must belong to only one currency type.

Expected behavior
• A vendor registered as HTG must only operate as an HTG vendor.
• A vendor registered as USD must only operate as a USD vendor.
• The same vendor must not be shown in both HTG and USD environments.
• Players should only see vendors matching the player's selected currency.

Important rule
Vendor currency is not only a display option. It controls:
• visibility
• wallet color
• withdrawal methods
• player access
• available payout methods
• gift card and payment compatibility

Developer note
The system should store vendor currency as a required field at signup and use it as a filter
throughout the platform.


1.2 Vendor wallet display color

Requirement
Vendor wallet balance must visually reflect the selected currency.

Expected behavior
• Vendor Wallet Balance HTG must be displayed in red
• Vendor Wallet Balance USD must be displayed in green

Purpose
This is to make the currency visually obvious and prevent confusion between HTG and USD
accounts.

Developer note
This should apply consistently:
• dashboard
• wallet page
• transaction screens
• withdrawal screens
• any summary cards showing balance


1.3 Vendor visibility by currency

Requirement
Vendors should only be visible to players of the same currency.

Expected behavior
• HTG vendors must only be visible to HTG players
• USD vendors must only be visible to USD players
• A vendor must not appear in both vendor lists
• Currency mismatch should never happen

Example
If Player A uses USD:
• Player A should only see USD vendors
If Player B uses HTG:
• Player B should only see HTG vendors

Developer note
This must be enforced in:
• vendor search
• vendor list
• vendor profile view
• player selection screens


1.4 Vendor signup approval workflow

Requirement
Vendors cannot become active immediately after signup.
A vendor must wait for Admin approval.

Expected signup flow
1. Vendor completes signup form
2. Vendor selects currency type
3. Vendor uploads required documents
4. Account is created with status = Pending
5. Vendor cannot fully access the app until Admin decision
6. Admin reviews account
7. Admin either approves or denies

Required vendor status flow
• Pending
• Approved
• Denied
• Suspended

Expected behavior after signup
After signing up as vendor:
• the application must remain in pending status
• vendor should not be treated as approved automatically
• vendor should see a clear message that the application is under review

Required message while pending
A vendor in pending status should see something like:
"Your account is pending Admin approval. You will receive a notification once a
decision has been made."

If approved
Vendor should:
• receive notification
• gain full vendor access
• become visible to eligible players in the same currency

If denied
Vendor should:
• receive notification
• receive explanation for denial
• remain blocked from vendor access until corrected or resubmitted

Required denial behavior
The denial notification must not just say "Denied".
It must include a reason, for example:
• missing document
• invalid ID
• business license issue
• incomplete information
• duplicate submission
• unsupported business type

Developer note
The denial reason must be stored and displayed in the vendor notification and/or status page.


1.5 Vendor document upload requirement

Requirement
Uploading documents is required during vendor signup, unless Admin intentionally bypasses it.

Required documents
At minimum:
• ID card
• business document / license

Expected behavior
• Signup form should not be completed without required documents
• Validation must block submission if required documents are missing
• Admin must have a manual override / bypass option when needed

Special case
If Admin bypasses document upload:
• vendor can still proceed to review
• vendor approval is still controlled by Admin

Developer note
This should be configurable per vendor by Admin, not by vendor.


1.6 Vendor withdrawals

Requirement
Vendors must be able to withdraw funds using multiple methods depending on the vendor's
currency type.

Required withdrawal methods
For USD vendors:
• Bank Transfer
• PayPal

For HTG vendors:
• MonCash

Important rule
Withdrawal methods shown to the vendor must depend on the vendor's currency.

Expected behavior
• USD vendor should not see MonCash as a primary currency-incompatible method unless
  intentionally configured by Admin
• HTG vendor should not see USD-only methods if not supported for HTG

Additional requirement
The app must explain clearly how much the vendor can withdraw and to which method.

Recommended UI behavior
Each withdrawal option should show:
• method name
• available limit
• processing note if needed
• selected currency

Developer note
Withdrawal method availability should be controlled by Admin configuration and vendor currency.


1.7 Vendor draw schedule – automatic open and close timer

This is one of the most important features and needs to be very explicit.

Purpose
Allow vendors to define the exact times when betting is open and closed for each state and each
draw time. This must automate betting availability so players cannot place bets outside allowed
hours.

Required UI fields

Draw State
Dropdown field to select the state.
Example:
• NY
• FL
• GA
• CT
• PA
• TX
• TN
• NJ

Draw Time
Dropdown field to select the draw session.
Example:
• Morning
• Midday
• Evening

Open Time
Custom input made of:
• hour box
• minute box
• AM/PM selector
Example: [06] [30] [AM]

Close Time
Custom input made of:
• hour box
• minute box
• AM/PM selector
Example: [11] [30] [AM]

Example layout:
  Draw State:  [ NY ▼ ]
  Draw Time:   [ Morning ▼ ]
  Open:        [ 06 ] [ 30 ] [ AM ]
  Close:       [ 11 ] [ 30 ] [ AM ]
               [ Save Schedule ]

Required logic
For each state and draw time, vendor should be able to save one schedule entry.
Example:
• NY + Morning = 06:30 AM to 11:30 AM
• NY + Midday  = 12:00 PM to 06:00 PM
• NY + Evening = 06:30 PM to 10:00 PM

System behavior
If current time is within the allowed schedule:
• betting is open
If current time is outside the allowed schedule:
• betting is closed

Required player-side impact
The Player app must respect this schedule automatically.
If a vendor schedule says the draw is closed:
• player must not be allowed to play
• play button should be disabled or blocked
• message should appear such as: "This draw is currently closed."

Validation rules
• Draw State is required
• Draw Time is required
• Open hour is required
• Open minute is required
• Open AM/PM is required
• Close hour is required
• Close minute is required
• Close AM/PM is required
• Open time must be before close time

Additional developer note
This feature should support separate schedule records per:
• vendor
• state
• draw time


1.8 Vendor play history

Requirement
Play history must contain more useful reporting information.

Required fields in play history
• Date
• Draw Time
• Draw State
• Number of players
• Total amount for all players together

Explanation
This is not just a simple list of plays.
The vendor should be able to understand:
• when the plays were made
• what draw they belong to
• how many players are involved
• how much total money is in that draw set

Example:
  Date: March 26, 2026
  State: NY
  Draw Time: Morning
  Number of Players: 25
  Total Amount: 4,500 HTG


1.9 Vendor play history export before results

Requirement
The vendor must be able to upload or export the play history file before results are known.

Purpose
This file may be sent to another party as a report before winners are determined.

What the pre-result file must include
• all plays entered
• player entries
• amounts
• date
• draw state
• draw time
• number groupings if needed

What it must NOT include
• winners
• winning amounts
Because results are not known yet.

Explanation
This is a reporting file used before outcome calculation.


1.10 Vendor play history after results

Requirement
After results are entered, the uploaded / exported file should reflect winners and total winning
amount.

What the post-result file must include
• all original plays
• matching winners
• total winning amount
• filters for easier search

Required filters
At minimum:
• by date
• by amount
• by draw state
• by draw time
• by winner / non-winner if possible

Purpose
This allows proper post-result reporting and payout tracking.

2.4 Wallet usage rule for gameplay

Critical rule
Players can only pay to play using the App Wallet.

This rule must be enforced everywhere
Players must NOT be able to:
• play directly with bank transfer
• play directly with Zelle
• play directly with CashApp
• play directly with PayPal
• play directly with debit card
• play directly with MonCash

Correct flow
1. Player adds money to wallet
2. Wallet balance increases
3. Player places bets using wallet balance only

Purpose
This keeps wallet accounting and payouts consistent.

2.6 Gift card buying flow

Requirement
Players should be able to buy gift cards from the website.

Important clarification
Gift cards are not purchased inside the app itself.
The app should redirect the player to the website to buy the correct gift card.

Required UI behavior in wallet
Under Gift Card option, there should be 2 choices:
• Buy
• Redeem

If player clicks Buy
The app should open the website directly.

Currency-specific behavior
• If player is using HTG currency, Buy should redirect to HTG gift card page
• If player is using USD currency, Buy should redirect to USD gift card page

Gift card purchase methods
For HTG gift cards:
• pay with MonCash

For USD gift cards:
• pay with Zelle
• CashApp
• PayPal
• Debit Card

Delivery after purchase
After successful gift card purchase, the PIN should be delivered by:
• Email
or
• WhatsApp


2.7 Gift card redeem flow

Requirement
Players must be able to redeem a gift card PIN inside the app.

Required behavior
When player clicks Redeem:
• show PIN entry field
• validate the PIN
• if valid, add money to wallet
• if invalid, show error message

Required success behavior
If PIN is correct:
• wallet balance updates immediately
• transaction is recorded
• gift card marked as used

Required error message
If PIN is incorrect:
"Incorrect PIN"

Additional developer note
PINs must not be reusable after successful redemption.
